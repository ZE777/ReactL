# 工作流程 (Workflow)：單元測試與自動化驗證

為防範「改了 A 卻壞掉 B」的慘劇，每次完成特徵模組 (Feature) 邏輯或是共用函式庫後，必須強制執行此測試工作流。

## Step 1: 測試範圍約定 (What to test?)
我們不追求虛榮的 100% 覆蓋率，而是專注測試高風險區塊：
1. **Utility Functions (`src/utils`)：** 這是最容易報錯的純邏輯區 (如：日期轉換、金額千分位、複雜的正則表達式)。**必須 100% 測試。**
2. **Custom Hooks (`src/features/*/hooks`)：** 處理 API 轉換、表單交互邏輯的 Hook。
3. **展示型組件 (Dumb Components)：** 不用每顆按鈕都測，但具備複雜變形的元件 (如動態 Table) 需要測試。

## Step 2: 撰寫測試檔 (Vitest / Jest)
測試檔案命名統一加上 `.test.ts` 或 `.spec.ts`，並直接與目標檔案**放在同一個資料夾 (Co-location)**。
```text
src/utils/
├── currencyFormat.ts
└── currencyFormat.test.ts  ← 測試檔就在旁邊
```

**測試撰寫範例：**
```typescript
import { expect, test, describe } from 'vitest';
import { formatCurrency } from './currencyFormat';

describe('金額格式化測試', () => {
  test('應能加上千分位與金錢符號', () => {
    expect(formatCurrency(1234567)).toBe('$1,234,567');
  });
  
  test('防呆：處理 Null 或未定義時不應崩潰', () => {
    expect(formatCurrency(undefined)).toBe('$0');
  });
});
```

## Step 3: 發起 PR 前的自動化阻擋
這套測試機制將會綁定進前一份文件的 **Husky Pre-commit Hook** 中。
開發者執行 `git commit` 時，不僅會跑 Lint，還會自動在背景跑 `npm run test:run`。只要有任何一個 Assert 失敗，代碼就絕對不允許進入主幹。
