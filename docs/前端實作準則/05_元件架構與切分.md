# 元件切分與架構維護性 (Component Architecture)

專案從小變大時，最常見的災難是「元件長達兩千行」或是「檔案彼此深度耦合」。此文件定義如何乾淨切分元件，確保長期維護性。

## 1. 目錄級別的關注點分離 (Feature-Driven Architecture)
不建議將專案的所有元件都丟到一個 `/components` 資料夾。推薦根據業務功能拆分 (如 Feature-Sliced Design)：
*   `/src/shared/ui/`：全域共用的基礎元件 (按鈕、輸入框、Modal 基底)。這些元件**不可以**知道業務邏輯。
*   `/src/features/`：具有特定商業邏輯的區塊 (如 `ShoppingCart`, `UserProfile`)。這裡面的元件可以牽涉 API 或是全域狀態。
*   `/src/pages/`：負責組合 Features 並處理路由參數。此層不做複雜邏輯，只做拼圖。

## 2. Smart vs Dumb Components (容器型與展示型)
*   **Dumb (展示型元件)：** 只負責「長相」。資料全靠 `props` 傳入，互動透過 `emits` 或 `callback` 傳出。不應該有 API 呼叫，極易於寫 Storybook 與 Unit Test。
*   **Smart (容器型/邏輯型元件)：** 負責「大腦」。處理 `useState`、抓取資料 (Fetch APIs)，處理好後將結果以 Props 的方式丟給下游的 Dumb Components 呈現。

## 3. Custom Hooks (自訂邏輯抽離)
當一個 Component 的 JavaScript 處理邏輯超過了一半篇幅時，就應該進行抽離：
*   **視圖層分離：** 把負責資料請求、表單驗證、或狀態處理的邏輯抽成特定的 Custom Hook (例如 `useLoginForm.js`)。
*   **主元件保持清爽：** Main Component 裡只要呼叫 `const { formData, errors, handleSubmit } = useLoginForm();`，剩下的行數專心撰寫 DOM 結構。

## 4. Prop Drilling 與 Context 的取捨
*   如果只是單純元件樹的上下層傳遞 (父傳子傳孫)，不需要立刻動用 Global Store (Redux/Pinia) 或 Context。
*   善用 `children` 組裝模式 (Composition Pattern)：在父層將區塊準備好，直接以 `children` 或 `slots` 的方式傳遞給版面元件，避免無意義的 props 隧道效應。
