# 前端全域狀態與 UI 管理守則

本專案在非同步的資料獲取 (API Fetch/Server State) 已經全權交由 **React Query** 負責。
因此，這份文件專門探討：**剩下來的那些「純前端 UI 狀態」(Client State) 該如何管理？**

## 1. 拒絕使用龐大的 Redux
過去的架構習慣將所有變數塞進 Redux。但在我們已經有 React Query 的今天，Redux 顯得過度臃腫（需要寫 Actions, Reducers, Dispatchers）。本專案全面棄用 Redux。

## 2. 工具選型：Zustand
我們採用 **Zustand** 作為全域狀態管理庫。它的特色是極度輕量、不需要用 React Context 提供者 (`<Provider>`) 包覆程式碼，而且沒有地獄級的樣板程式。

### 何時該放進 Zustand？
只有當這個狀態 **「必須跨越好幾個不相關的頁面或層級共用」** 時才使用。
例如：
1. 展開/收合側邊攔導覽 (Sidebar Toggle)。
2. 深淺色模式偏好設定 (Dark/Light Mode)。
3. 使用者目前正在進行的多頁面問卷輸入暫存 (Multi-step Form)。
4. 整個系統全域發送的通知系統 (Global Toast Notifications)。

### 何時不該用 Zustand？
*   如果是單一頁面內、父子組件傳遞的狀態 → 繼續用單純的 `useState` 或局部 `Context` 即可。
*   如果是 API 取回來的資料 → 回落到 `useQuery` 管理。

## 3. Zustand 的實作範疇 (Store 分離)
我們應該依據領域切分 Store，不要弄出一個肥大的 `useGlobalStore`。
```typescript
import { create } from 'zustand';

interface UIState {
  isSidebarOpen: boolean;
  toggleSidebar: () => void;
}

// 建立局部且針對性強的 Store
export const useUIStore = create<UIState>((set) => ({
  isSidebarOpen: false,
  toggleSidebar: () => set((state) => ({ isSidebarOpen: !state.isSidebarOpen })),
}));
```
我們甚至可以直接在這裡掛載 middleware，達成諸如 **LocalStorage 自動備份** 的強大功能，適合用來存儲使用者的 UI 偏好習慣。

## 4. Provider 是否必要：Zustand 不需要、React Query 需要

不同的狀態管理工具對 Provider 的依賴不同，初期容易混淆：

| 工具 | 需要 Provider? | 原因 |
|------|--------------|------|
| **Zustand** | ❌ 不需要 | Store 是 module-level singleton，import 就能用 |
| **React Query** | ✅ 必須 | `useQuery` / `useMutation` 從 React Context 讀取 `QueryClient` |
| **Context API** | ✅ 本來就靠 Provider | — |
| `useState` / `useReducer` | ❌ 不需要 | 只有當前組件樹存取 |

### Next.js App Router 的 Provider 組裝

對外站採 Next.js 時，Root Layout 是 Server Component，但 `QueryClientProvider` 必須是 Client Component。橋樑是 `src/app/providers/` 資料夾（拆檔，每個 Provider 一份），由 `app/layout.tsx` 引用 `<Providers>` 組裝。

> **關鍵紀律 — QueryClient 必須用 `useState(() => new QueryClient(...))` 初始化**：寫在 module 頂層會在 SSR 跨使用者共享 cache，造成資料外洩。
