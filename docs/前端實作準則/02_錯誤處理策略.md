# 錯誤處理策略 (Error Handling Strategy)

本指南旨在為前端專案建立標準化的「錯誤攔截與錯誤呈現」機制，確保在網路不穩、API 報錯或元件渲染異常時，系統能展現高度的「韌性 (Resilience)」且不讓使用者看見白畫面。

## 1. 錯誤的分類與處理層級

前端面臨的錯誤主要分為三大類，處理層級各有不同：
*   **執行期渲染錯誤 (Runtime/Rendering Errors)：** 元件在渲染時因為資料為 undefined 導致崩潰。 -> **由 Error Boundaries (錯誤邊界) 處理。**
*   **API 網路請求錯誤 (Network/HTTP Errors)：** 後端回傳 4xx 或 5xx 錯誤。 -> **由 API Interceptors (攔截器) 全域處理與區域 Catch 處理。**
*   **預期內業務邏輯錯誤 (Business Logic Errors)：** 例如庫存不足、密碼錯誤。 -> **由 UI 元件捕捉並顯示 Toast/表單提示。**

## 2. API 攔截器 (Axios Interceptors) 實作規範

所有的外部請求必須經過統一的實體 (Instance)，不可在元件中隨處宣告 `fetch`。
*   **Request Interceptor (請求攔截)：** 負責將 Token 動態塞入 Header。
*   **Response Interceptor (回應攔截)：** 
    *   `401 Unauthorized`：觸發 Token Refresh 流程（完整實作詳見 `SKILL_API層與攔截快取.md`）。
        *   **Token Refresh 競態條件處理：** 當多個並發請求同時遇到 401 時，僅第一個請求觸發 Refresh，其餘請求進入 Promise Queue 等待。Refresh 成功後，所有等待中的請求以新 Token 重新發送（Replay）；Refresh 失敗則統一清空 Token 並導回登入頁。
        *   **禁止直接 `window.location.href = '/login'`：** 在未嘗試 Refresh 前，不可直接跳轉登入頁，否則使用者在正常操作中會因 Token 自然過期而被強制登出，體驗極差。
    *   `403 Forbidden`：導向權限不足的提示頁面。
    *   `500 Internal Server Error`：觸發全域的 Toast 通知「系統遭遇異常，請稍後再試」。

## 3. Error Boundaries (錯誤邊界設計：白畫面的終極解法)

前端專案嚴禁因為單一子元件的邏輯報錯，導致整個 DOM 樹崩解（白畫面）。
*   **全域 Error Boundary：** 放在 App 的最上層，當遇到無法恢復的毀滅性錯誤時，展示「糟糕，系統異常」並提供「重新整理」按鈕的 Fallback UI。
*   **局部 Error Boundary：** 針對高風險或外部依賴的區塊（如：廣告區塊、第三方圖表），使用獨立的 Error Boundary 包裹。若圖表壞掉，只有圖表區顯示「載入失敗」，而不影響結帳或側邊欄等主畫面的獨立運作。

### 實作方案建議 (以 React 為例)
不建議每次專案都徒手撰寫笨重的 Class Component。強烈建立統一引入輕量套件 `react-error-boundary` 進行攔截：

```jsx
import { ErrorBoundary } from 'react-error-boundary';

// 定義崩潰時要展示的備用畫面 (Fallback UI)
function GlobalFallback({ error, resetErrorBoundary }) {
  return (
    <div className="error-container p-4 bg-red-50">
      <h3>頁面發生未預期錯誤</h3>
      <p>{error.message}</p>
      <button onClick={resetErrorBoundary}>再試一次</button>
    </div>
  );
}

// 在核心元件外層套上防護罩
function App() {
  return (
    <ErrorBoundary FallbackComponent={GlobalFallback}>
       <AppDashboard />
    </ErrorBoundary>
  );
}
```

## 4. 防呆與重試機制 (Retry & Fallback)

*   在發送刪除、付款等毀滅性或不可逆的 API 時，必須實作防連點 (Debounce / 按鈕 Disable 狀態)。
*   非破壞性的資料獲取（如：拉取商品清單），可利用如 React Query/SWR 自帶的機制，設定失敗重試次數 (Retries)，增加網路閃斷時的成功率。

### 4.1 樂觀更新操作的離線防護

帶有**樂觀更新（Optimistic Update）** 的 mutation（如 Toggle 開關、即時排序），離線處理不可只靠 Axios `timeout`。

**根本原因：** 瀏覽器離線時，`XMLHttpRequest` 不會立即開始，而是被放進網路佇列等待恢復。Axios 的 `timeout` 是 XHR 層的 `setTimeout`，XHR 尚未啟動時計時器根本不會跑，導致使用者等很久卻看不到任何錯誤訊息，甚至網路恢復後請求被自動補發（非預期的延遲執行）。

**正確防護模式：**

```tsx
mutationFn: async ({ id, enabled }) => {
  // 離線時 XHR 進佇列而非立即失敗，須在此提前攔截
  if (!navigator.onLine) throw new Error('網路已斷線')
  return unwrap(await api.put(`/items/${id}`, { enabled }, { timeout: 5000 }))
},
onError: (e: AxiosError<ApiError>, _, context) => {
  // 回滾樂觀更新
  if (context?.prev) queryClient.setQueryData(['items'], context.prev)
  toast('error', e.response?.data?.detail ?? (e as Error).message ?? '操作失敗')
},
```

**規則：**
- 所有帶樂觀更新的 mutation 必須在 `mutationFn` 開頭加 `navigator.onLine` 檢查
- Axios timeout 設定 5000ms（作為伺服器無回應的第二道防線）
- `onError` 使用 `e.response?.data?.detail ?? e.message` 同時覆蓋後端錯誤與離線錯誤訊息

## 5. 錯誤情境對照表（UI 選用規範）

每種錯誤情境對應固定的 UI 表現，不可混用：

### HTTP 狀態碼處理分工

| 狀態碼 | 情境 | 處理層 | UI 方式 | 說明 |
|--------|------|--------|---------|------|
| **400** | 後端欄位驗證失敗 | 元件層 | 行內錯誤（RHF `setError`）| 對應欄位旁顯示，不做跳轉 |
| **401** | 未登入 / Token 過期 | Axios 攔截器 | redirect `/login` | 見第 2 節 Token Refresh 規範 |
| **403** | 已登入但權限不足 | Axios 攔截器 | Toast 紅色「您沒有此操作的權限」| 留在原頁，不跳轉 |
| **404** | 頁面路由不存在 | Router 層 | 404 錯誤頁面 | 整頁替換 |
| **404** | API 資源不存在 | 元件層 | 行內提示「找不到資料」| 不整頁崩潰 |
| **409** | 資料衝突（重複名稱等）| 元件層 | 行內錯誤（靠近操作位置）| 後端回傳 detail 直接顯示 |
| **422** | 語義錯誤（格式對但不合規）| 元件層 | 行內錯誤（同 400）| 對應欄位旁顯示 |
| **429** | 請求頻率過高（AI API 額度）| Axios 攔截器 | Toast 橘色「請求頻率過高，請稍後再試」| 特別說明 AI 額度情境 |
| **500** | 伺服器內部錯誤 | Axios 攔截器 | Toast 紅色「伺服器發生錯誤，請稍後再試」| 不暴露錯誤細節 |
| **502** | 後端服務掛掉 | Axios 攔截器 | Toast 紅色「服務暫時無法連線」| |
| **503** | 系統維護中 | Axios 攔截器 | Toast 橘色「系統維護中，請稍後再試」| |
| **504** | 請求逾時 | Axios 攔截器 | Toast 橘色「請求逾時，請重新操作」| |

### 非 HTTP 錯誤

| 類型 | 處理層 | UI 方式 | 說明 |
|------|--------|---------|------|
| 網路斷線 | Axios 攔截器 | Toast 橘色「網路連線異常，請確認網路狀態」| `!error.response` 判斷 |
| Axios 逾時 | Axios 攔截器 | Toast 橘色「連線逾時，請稍後再試」| `error.code === 'ECONNABORTED'` |
| 表單前端驗證失敗 | 元件層 | 欄位下方紅字（RHF inline）| 不送出 API |
| 頁面資料載入失敗 | 元件層 | 行內 ErrorMessage + 重試按鈕 | 不整頁崩潰 |
| React 元件崩潰 | Error Boundary | Fallback UI + 重新整理按鈕 | 見第 3 節 |
| 列表無資料 | 元件層 | EmptyState 元件（說明 + 操作按鈕）| 不可顯示空白區域 |
| 危險操作（刪除等）| 元件層 | Modal 確認框 | 需要使用者主動確認 |

## 6. 後端錯誤格式規範（.NET ProblemDetails）

後端統一使用 RFC 7807 ProblemDetails 格式回傳錯誤，前端 Axios interceptor 統一解析：

```json
// 欄位驗證錯誤（400）→ 前端對應到 RHF setError
{
  "type": "ValidationError",
  "title": "輸入資料驗證失敗",
  "status": 400,
  "errors": {
    "name": ["名稱為必填"],
    "systemPrompt": ["提示詞至少 10 個字"]
  }
}

// 系統錯誤（500）→ 只給 traceId，不暴露 stack trace
{
  "type": "InternalError",
  "title": "系統發生錯誤",
  "status": 500,
  "traceId": "abc123"
}
```
