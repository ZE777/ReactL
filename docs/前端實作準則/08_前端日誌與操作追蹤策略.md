# 前端日誌與操作追蹤策略 (Frontend Logging & Telemetry)

當使用者回報「網頁點了沒反應」時，我們不能只回「在我電腦上是好的」。前端必須具備完整的 Log 追蹤與軌跡還原能力。

## 1. 前端 Log 紀錄的價值與工具
不同於後端 Log 主要在追蹤 Database 與 Server 效能，前端 Log 在於「追蹤使用者的操作路徑與瀏覽器端的異常」。
*   **強烈建議導入專業 Telemetry 服務：** 例如 **Sentry**, **Datadog RUM**, 或是 **LogRocket**。避免自行用 `console.log` 人工發送 API（因為容易遺失且耗費頻寬）。

## 2. 我們應該記錄什麼？(What to Log)
*   **未捕捉的例外 (Uncaught Exceptions)：** 所有的白畫面、執行期 Error，必須全數送往追蹤服務（可整合先前定義的 `ErrorBoundary`，在抓到錯誤時觸發 `Sentry.captureException`）。
*   **重要的業務流程 (Business Tracing)：**
    *   使用者抵達結帳頁，但 API 回傳Timeout。
    *   第三方金流套件初始化失敗。
    *   超過 3 秒沒有回應的 API 請求（被前端 Axios Interceptor 抓到）。
*   **使用者軌跡 (Breadcrumbs)：** 記錄使用者在崩潰前做了什麼（他點擊了「送出訂單」-> 填換了「地址欄位」-> 發生崩潰）。

## 3. Session Replay (畫面與操作還原)
這是您提到的「未來透過紀錄還原客戶操作」的最佳解法。
*   **DOM 突變紀錄機制：** 透過導入工具（如 **LogRocket** 或 **Sentry Session Replay**），它們會在背景以極低效能消耗記錄每一次 DOM 的變化與滑鼠軌跡。
*   **效果：** 當收到 Bug 報修時，工程師能直接在後台「播放」該使用者當機前幾十秒的網頁影片操作錄影，精準找出復現步驟。

## 4. 資安與隱私防護底線 (Data Masking)
在記錄使用者操作的心中，**絕對不能違反隱私權與 GDPR**。
*   **PII 屏蔽 (Masking Personally Identifiable Information)：** 前端回傳的 Log 以及 Session Replay 的畫面，**必須設定遮罩機制**。密碼輸入框、信用卡號、身分證字號，甚至是用戶真實姓名，在發送回追蹤伺服器前都必須被屏蔽成 `****`。
*   **這點是最嚴格的警戒線：** 設計 Logging 機制時，第一步就是設定被屏蔽的 DOM class (如 `sentry-mask`)，確保絕不把客戶隱私送出給任何服務商。
