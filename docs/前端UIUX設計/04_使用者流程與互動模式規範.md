# 使用者流程與互動模式規範 (User Flow & Interaction Patterns)

本文件定義專案中通用的互動模式與 UX 設計規範，確保使用者在不同頁面與功能中擁有一致且可預測的操作體驗。與 `04_微互動與體驗指南` 互補 — 該文件偏重動畫技術實作，本文件聚焦於 UX 行為與流程設計。

## 1. 使用者流程設計原則 (User Flow Principles)

### 1.1 核心原則

*   **最少步驟原則：** 使用者完成任務的步驟數應盡可能少。每增加一個步驟，流失率增加約 20%
*   **可逆性原則：** 使用者的操作應可撤銷或返回，不可將使用者鎖死在單向流程中
*   **可見性原則：** 系統狀態、進度、可用操作必須清楚可見，不讓使用者猜測
*   **容錯原則：** 系統應預防錯誤、而非僅在錯誤後提示；當錯誤發生時，提供明確的修正路徑

### 1.2 多步驟流程 (Multi-Step Flow / Wizard)

適用於車輛租借、訂單建立等複雜流程：

*   **進度指示器：** 頂部顯示步驟指示器（Step Indicator），標明當前步驟與總步驟數
*   **步驟可回溯：** 使用者可點擊先前的步驟回到修改，不可只有「上一步」按鈕
*   **資料暫存：** 切換步驟時保留已填寫的資料，避免使用者重填
*   **最終確認：** 最後一步提供完整的資料摘要，讓使用者在送出前確認

```tsx
// 步驟指示器範例
function StepIndicator({ steps, currentStep }) {
  return (
    <nav aria-label="租借流程進度">
      <ol className="flex items-center gap-2">
        {steps.map((step, index) => (
          <li key={step.id} className="flex items-center gap-2">
            <button
              onClick={() => goToStep(index)}
              disabled={index > currentStep}
              aria-current={index === currentStep ? 'step' : undefined}
              className={cn(
                "flex items-center gap-2 rounded-full px-3 py-1",
                index === currentStep && "bg-brand-primary-500 text-white",
                index < currentStep && "bg-brand-primary-100 text-brand-primary-700",
                index > currentStep && "bg-neutral-100 text-neutral-400"
              )}
            >
              <span>{index + 1}</span>
              <span className="hidden sm:inline">{step.label}</span>
            </button>
          </li>
        ))}
      </ol>
    </nav>
  );
}
```

## 2. 搜尋與篩選 (Search & Filter)

### 2.1 搜尋行為

| 設計決策 | 規範 |
|----------|------|
| 搜尋觸發 | 輸入後延遲 300ms 自動搜尋（Debounce），或按 Enter 觸發。兩者皆可，同一專案須統一 |
| 搜尋建議 | 輸入 2 字元以上時顯示 Autocomplete 下拉，最多 8 筆建議 |
| 無結果 | 顯示友善的空狀態：說明文字 + 建議操作（修改關鍵字、清除篩選、瀏覽分類） |
| 搜尋歷史 | 搜尋框聚焦時顯示最近 5 筆搜尋記錄（localStorage），可一鍵清除 |
| 搜尋結果高亮 | 搜尋關鍵字在結果中以 `<mark>` 高亮標示 |

### 2.2 篩選行為

*   **篩選條件可見性：** 已啟用的篩選條件以 Tag/Chip 顯示在結果上方，每個 Tag 可單獨移除
*   **清除所有篩選：** 提供「清除全部」按鈕，一鍵回到未篩選狀態
*   **即時更新：** 篩選變更後立即更新結果，不需額外點擊「套用」按鈕
*   **篩選計數：** 篩選按鈕顯示已啟用的篩選數量（如「篩選 (3)」）
*   **URL 同步：** 篩選條件應同步至 URL query params，支援分享與書籤

```
// URL 同步範例
/vehicles?type=sedan&brand=toyota&priceRange=1000-2000&sort=price-asc
```

### 2.3 手機端篩選

*   篩選面板以 **Bottom Sheet** 或 **全螢幕 Drawer** 呈現，不使用 Dropdown
*   底部固定「查看 N 筆結果」按鈕，即時顯示篩選後的結果數量
*   「清除全部」按鈕位於面板頂部

## 3. 列表呈現與分頁 (List & Pagination)

### 3.1 分頁 vs 無限滾動

| 方式 | 適用情境 | 優勢 | 劣勢 |
|------|----------|------|------|
| 分頁 (Pagination) | 後台管理列表、需精確定位的資料 | 可書籤、SEO 友善、效能可控 | 多次點擊 |
| 無限滾動 (Infinite Scroll) | 社群動態、商品瀏覽 | 流暢體驗、探索性強 | 無法書籤、Footer 不可達 |
| 載入更多 (Load More) | 折衷方案 | 使用者控制節奏 | 不知總量 |

### 3.2 分頁規範

*   **每頁筆數：** 預設 20 筆，提供 10 / 20 / 50 / 100 的切換選項
*   **頁碼顯示：** 顯示首頁、末頁、當前頁及前後各 1~2 頁，中間以 `...` 省略
*   **總筆數：** 列表上方顯示「共 N 筆結果」
*   **排序：** 提供明確的排序 Dropdown（如「依價格低到高」），目前排序方式應可見

### 3.3 無限滾動規範

*   距離底部 200px 時觸發下一頁載入
*   載入中顯示 Skeleton Loader（非 Spinner）
*   載入失敗提供「重試」按鈕
*   提供「回到頂部」浮動按鈕（滾動超過 2 屏後出現）

## 4. 彈窗與疊層 (Modal, Drawer, Popover, Toast)

### 4.1 使用時機判斷

| 元件 | 使用時機 | 特性 |
|------|----------|------|
| **Modal (Dialog)** | 需要使用者做出決策或確認的阻斷式操作 | 背景遮罩、Focus Trap、必須回應才能繼續 |
| **Drawer** | 展示詳細資訊或次要表單 | 從側邊/底部滑入、可選擇性關閉、不強制回應 |
| **Popover** | 元素附近的小型資訊或選單 | 相對定位、點擊外部關閉、輕量 |
| **Toast** | 操作結果通知 | 非阻斷、自動消失（3~5秒）、螢幕角落 |
| **Alert / Banner** | 全頁/全區域的重要通知 | 持續顯示直到使用者關閉或狀態改變 |

### 4.2 確認對話框 (Confirmation Dialog)

用於不可逆操作（刪除、取消訂單等）：

*   **標題：** 明確描述操作（「確定要刪除此車輛？」而非「確定嗎？」）
*   **內容：** 說明操作後果（「刪除後將無法復原，相關的 3 筆租借記錄也會一併移除」）
*   **按鈕：** 主要動作使用具體動詞（「刪除車輛」而非「確定」），危險操作使用紅色按鈕
*   **按鈕順序：** 取消在左（次要）、確認在右（主要）

```tsx
// 確認對話框範例
<Dialog>
  <DialogTitle>確定要刪除「Toyota Camry」？</DialogTitle>
  <DialogDescription>
    刪除後將無法復原。此車輛目前有 3 筆進行中的租借記錄。
  </DialogDescription>
  <DialogFooter>
    <Button variant="ghost" onClick={onCancel}>取消</Button>
    <Button variant="destructive" onClick={onConfirm}>刪除車輛</Button>
  </DialogFooter>
</Dialog>
```

### 4.3 Toast 通知規範

| 類型 | 持續時間 | 樣式 | 範例 |
|------|----------|------|------|
| Success | 3 秒 | 綠色左邊條 + ✓ 圖示 | 「車輛已成功新增」 |
| Error | 不自動消失（需手動關閉） | 紅色左邊條 + ✕ 圖示 | 「儲存失敗，請稍後重試」 |
| Warning | 5 秒 | 橙色左邊條 + ⚠ 圖示 | 「庫存即將不足」 |
| Info | 5 秒 | 藍色左邊條 + ℹ 圖示 | 「系統將於 10 分鐘後維護」 |

*   Toast 堆疊方向：從上往下（最新在最上方），最多同時顯示 3 則
*   位置：桌面 — 右上角；手機 — 頂部全寬

## 5. 空狀態設計 (Empty States)

每個列表、搜尋結果、或動態內容區域都必須設計空狀態：

### 5.1 空狀態類型

| 場景 | 設計要素 | 範例 |
|------|----------|------|
| **首次使用** | 插圖 + 歡迎文案 + 引導操作 CTA | 「還沒有車輛資料，立即新增第一輛車輛」 |
| **搜尋無結果** | 插圖 + 原因說明 + 建議操作 | 「找不到符合條件的車輛。試試放寬篩選條件？」 |
| **清空後** | 插圖 + 狀態說明 | 「所有通知已讀取完畢」 |
| **權限不足** | 鎖定圖示 + 說明 + 聯繫管道 | 「您沒有查看此頁面的權限，請聯繫管理員」 |
| **載入失敗** | 錯誤圖示 + 原因 + 重試按鈕 | 「資料載入失敗，請檢查網路連線後重試」 |

### 5.2 空狀態設計原則

*   **不留空白：** 絕對不可顯示空白頁面或只有表頭沒有表身
*   **有行動力：** 每個空狀態至少包含一個 CTA 按鈕，引導使用者下一步
*   **正向語氣：** 使用友善、正面的語氣，避免責備使用者

## 6. 錯誤頁面 (Error Pages)

### 6.1 HTTP 錯誤頁面

| 頁面 | 標題 | 內容 | 操作 |
|------|------|------|------|
| **404** | 找不到頁面 | 「您要找的頁面可能已被移除或網址有誤」 | 返回首頁、搜尋 |
| **403** | 沒有存取權限 | 「您沒有查看此頁面的權限」 | 返回上一頁、聯繫管理員 |
| **500** | 系統發生錯誤 | 「很抱歉，系統暫時無法處理您的請求」 | 重新整理、返回首頁 |
| **503** | 系統維護中 | 「系統正在進行維護，預計 HH:MM 恢復」 | 預估恢復時間 |

### 6.2 設計規範

*   包含品牌元素（Logo、品牌色），讓使用者知道仍在同一個網站
*   提供至少一個明確的返回路徑（如「返回首頁」按鈕）
*   404 頁面可加入搜尋功能或熱門頁面連結
*   不暴露技術細節（如 stack trace、server error message）

## 7. 載入狀態 (Loading States)

### 7.1 載入策略選擇

| 預估等待時間 | 載入指示方式 |
|-------------|-------------|
| < 300ms | 不顯示任何載入指示（避免閃爍） |
| 300ms ~ 2s | 在操作元素上顯示 Spinner（如按鈕內的 Loading） |
| 2s ~ 10s | 顯示 Skeleton Screen 佔位 |
| > 10s | 顯示進度條 (Progress Bar) + 預估剩餘時間 |

### 7.2 Skeleton Screen 規範

*   骨架形狀應反映實際內容的排版結構（矩形代表文字、圓形代表頭像）
*   使用 Shimmer 動畫（左到右的漸層閃爍），而非靜態灰色區塊
*   骨架屏數量應反映實際每頁筆數（而非只顯示 1~2 個）
*   骨架屏到真實內容的切換不應造成 Layout Shift

## 8. 表單互動進階規範 (Advanced Form UX)

與 `04_微互動與體驗指南` 中的基礎表單規範互補：

### 8.1 漸進式揭露 (Progressive Disclosure)

*   複雜表單不要一次展示所有欄位，依邏輯分組逐步揭露
*   使用條件式顯示：選擇「法人」時才顯示統一編號欄位
*   進階選項放在「更多設定」的可展開區塊中

### 8.2 自動完成與智慧預設

*   地址欄位提供 Autocomplete
*   日期選擇器預設為合理值（如租借起始日預設明天）
*   數量選擇器提供常用選項的快捷按鈕

### 8.3 多欄位驗證時機

| 時機 | 行為 | 適用情境 |
|------|------|----------|
| `onChange` | 即時驗證（每次輸入觸發） | 密碼強度指示器 |
| `onBlur` | 焦點離開時驗證 | 一般文字/數字欄位 |
| `onSubmit` | 送出時驗證 | 最終防線，捕捉未觸發 onBlur 的欄位 |

**原則：** 驗證時機不早於 `onBlur`（避免使用者還在輸入就顯示錯誤），但密碼強度等正向回饋可使用 `onChange`。

### 8.4 Modal 新增 / 編輯 按鈕狀態規則

後台所有 Modal 表單統一遵守以下規則，確保操作意圖明確、防止無效送出：

| 模式 | 送出按鈕亮起條件 | 技術依據 |
|------|----------------|---------|
| **新增** | 所有必填欄位皆通過驗證 | `isValid === true` |
| **編輯** | 至少一個欄位與原始值不同 | `isDirty === true` |

#### 驗證流程（新增模式）

1. Modal 開啟時立即呼叫 `trigger()` — 必填欄位顯示紅框提示，送出按鈕維持 disabled
2. 使用 `mode: 'onChange'` 實時驗證，所有必填欄位填完後 `isValid → true`，按鈕才亮起
3. Modal 關閉時（`if (!isOpen) return null` unmount）表單狀態完全重置，下次開啟重新從空白計算

#### 驗證流程（編輯模式）

1. Modal 開啟時欄位預填現有資料，`isDirty` 初始為 `false`，按鈕 disabled
2. 任一欄位修改後 `isDirty → true`，按鈕亮起；還原所有變更後自動回到 disabled

#### 實作注意事項

- **條件式欄位**（如 LINE 專屬的 Channel Secret）搭配 `shouldUnregister: true`，確保切換平台時不殘留舊值影響 `isValid`
- **程式設值**（如 AI 模型自動帶入第一個可用項）必須加 `{ shouldValidate: true }` 讓 `isValid` 同步更新
- `isValid` / `isDirty` 透過 `onValidChange` / `onDirtyChange` callback 提升至父層，由父層 Modal footer 統一控制按鈕 disabled
- 若表單按鈕在元件內部（如 PersonaForm），直接在元件內計算有效性：`name ≥ 2 字 && 必填 section 皆非空`
