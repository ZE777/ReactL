# 無障礙設計守則 (Accessibility Guidelines)

本文件定義專案的無障礙 (a11y) 實作標準，以 **WCAG 2.2 AA** 為最低合規要求。無障礙不是加分項目，而是專業產品的基本品質門檻。公開網站（面向客戶）與後台管理介面（面向內部人員）皆須遵守。

## 1. 語意化 HTML (Semantic HTML)

### 1.1 Landmark Roles

每個頁面必須具備完整的 Landmark 結構，讓螢幕閱讀器使用者能快速跳轉至目標區域：

```html
<body>
  <header>     <!-- 網站標頭、Logo、全域導覽 -->
    <nav aria-label="主選單">...</nav>
  </header>
  <main>       <!-- 頁面主要內容，每頁僅一個 -->
    <article>  <!-- 獨立完整的內容區塊（如文章、商品詳情） -->
    <section aria-labelledby="section-title">  <!-- 有標題的內容分區 -->
  </main>
  <aside>      <!-- 側邊欄、相關連結 -->
  <footer>     <!-- 網站頁尾、版權資訊 -->
</body>
```

### 1.2 Heading 層級

*   **H1 唯一性：** 每頁僅一個 `<h1>`，代表頁面主題
*   **不可跳級：** h1 → h2 → h3 依序遞減，禁止 h1 → h3（跳過 h2）
*   **禁止以外觀選擇 Heading：** 需要大字不代表要用 `<h2>`，應使用 CSS class 控制外觀，Heading 只反映文件結構

### 1.3 互動元素語意

| 行為 | 正確元素 | 錯誤做法 |
|------|----------|----------|
| 跳轉頁面/導覽 | `<a href="...">` | `<div onClick>` / `<span onClick>` |
| 觸發動作（送出、開啟 Modal） | `<button type="button">` | `<a href="#">` / `<div role="button">` |
| 送出表單 | `<button type="submit">` | `<a onClick>` |
| 可選項目 | `<input type="checkbox">` / `<input type="radio">` | `<div onClick>` + 自製切換 |

**原則：** 永遠優先使用原生 HTML 元素，它們內建鍵盤支援與螢幕閱讀器語意。只有在原生元素無法滿足需求時，才使用 ARIA 屬性補強。

## 2. 鍵盤導覽 (Keyboard Navigation)

### 2.1 基本要求

*   **所有互動元素必須可聚焦：** 使用原生互動元素（`<button>`, `<a>`, `<input>`）自動獲得焦點支援
*   **Tab 順序合理：** Focus 順序須符合視覺閱讀順序（從上到下、從左到右），不可使用 `tabindex` 值大於 0 來強制改變順序
*   **Focus 樣式必須可見：**
    ```css
    /* ❌ 禁止 — 移除 Focus 指示器 */
    *:focus { outline: none; }

    /* ✅ 正確 — 自訂 Focus 樣式 */
    *:focus-visible {
      outline: 2px solid var(--brand-primary-500);
      outline-offset: 2px;
      border-radius: 4px;
    }
    ```

### 2.2 鍵盤操作慣例

| 按鍵 | 行為 |
|------|------|
| `Tab` | 移動焦點至下一個互動元素 |
| `Shift + Tab` | 移動焦點至上一個互動元素 |
| `Enter` | 啟動連結或按鈕 |
| `Space` | 啟動按鈕、切換 Checkbox |
| `Escape` | 關閉 Modal / Dropdown / Popover |
| `Arrow Keys` | 在 Tab、Menu、Listbox、Radio Group 等複合元件中移動 |
| `Home / End` | 跳至列表首項 / 末項 |

### 2.3 Focus Management（焦點管理）

*   **Modal 開啟時：** 焦點移至 Modal 內第一個互動元素，並實作 Focus Trap（Tab 循環在 Modal 內部）
*   **Modal 關閉後：** 焦點回到觸發 Modal 的原始元素
*   **動態內容載入後：** 若新內容需要使用者注意，將焦點移至新內容區域或使用 `aria-live`
*   **路由切換後 (SPA)：** 焦點應移至新頁面的 `<main>` 或 `<h1>`，避免焦點遺失在已移除的 DOM 元素上

```tsx
// Focus Trap 範例 — 使用 @radix-ui/react-focus-scope
import * as FocusScope from '@radix-ui/react-focus-scope';

function Modal({ open, onClose, children }) {
  if (!open) return null;
  return (
    <div role="dialog" aria-modal="true" aria-labelledby="modal-title">
      <FocusScope.Root trapped>
        <h2 id="modal-title">對話標題</h2>
        {children}
        <button onClick={onClose}>關閉</button>
      </FocusScope.Root>
    </div>
  );
}
```

## 3. ARIA 屬性使用指南

### 3.1 核心原則：No ARIA is better than bad ARIA

ARIA 不能修復語意錯誤的 HTML。錯誤的 ARIA 比沒有 ARIA 更糟糕 — 它會誤導螢幕閱讀器使用者。

### 3.2 常用 ARIA 屬性

| 屬性 | 用途 | 範例 |
|------|------|------|
| `aria-label` | 為沒有可見文字的元素提供標籤 | `<button aria-label="關閉對話框"><XIcon /></button>` |
| `aria-labelledby` | 引用另一個元素作為標籤 | `<section aria-labelledby="section-title">` |
| `aria-describedby` | 引用另一個元素作為補充描述 | `<input aria-describedby="password-hint">` |
| `aria-expanded` | 標示可展開元素的開合狀態 | `<button aria-expanded="true">展開選單</button>` |
| `aria-hidden` | 對螢幕閱讀器隱藏裝飾性元素 | `<span aria-hidden="true">🔍</span>` |
| `aria-live` | 標記動態更新區域 | `<div aria-live="polite">已新增至購物車</div>` |
| `aria-current` | 標示目前所在位置 | `<a aria-current="page">首頁</a>` |
| `aria-invalid` | 標示表單欄位驗證失敗 | `<input aria-invalid="true" aria-describedby="email-error">` |
| `aria-busy` | 標示區域正在載入中 | `<div aria-busy="true">載入中...</div>` |
| `aria-disabled` | 標示元素已禁用（保持可聚焦） | `<button aria-disabled="true">儲存</button>` |

### 3.3 動態內容通知 (Live Regions)

```tsx
// Toast / 通知的 aria-live 使用
function ToastContainer({ messages }) {
  return (
    <div aria-live="polite" aria-atomic="true" className="sr-only">
      {messages.map(msg => (
        <p key={msg.id}>{msg.text}</p>
      ))}
    </div>
  );
}

// 表單錯誤的即時回饋
<input 
  id="email"
  aria-invalid={!!errors.email}
  aria-describedby={errors.email ? 'email-error' : undefined}
/>
{errors.email && (
  <p id="email-error" role="alert">{errors.email.message}</p>
)}
```

## 4. 色彩與對比度 (Color & Contrast)

### 4.1 對比度要求

| 元素類型 | 最低對比度 (AA) | 建議對比度 (AAA) |
|----------|-----------------|------------------|
| 一般文字（< 18px） | 4.5:1 | 7:1 |
| 大字（≥ 18px bold 或 ≥ 24px） | 3:1 | 4.5:1 |
| UI 元件邊界（按鈕邊框、輸入框邊框） | 3:1 | — |
| 非文字元素（圖示、圖表） | 3:1 | — |

### 4.2 色彩使用原則

*   **不依賴顏色傳達資訊：** 錯誤狀態除了紅色標記，必須同時有圖示或文字說明
*   **表單驗證：** 錯誤欄位除了紅色邊框，必須有文字錯誤訊息
*   **圖表/數據：** 不同系列除了色彩區分，還須使用圖案、標記或文字標籤
*   **連結辨識：** 段落中的連結除了顏色差異，建議加上底線（至少在 hover 時顯示）

## 5. 圖片與多媒體 (Images & Media)

### 5.1 圖片替代文字

| 圖片類型 | alt 屬性處理 |
|----------|-------------|
| 資訊性圖片（傳達內容） | `alt="具體描述圖片內容"` |
| 功能性圖片（如連結圖示） | `alt="描述功能，如：前往首頁"` |
| 裝飾性圖片 | `alt=""` 或 `aria-hidden="true"` |
| 複雜圖片（圖表、資訊圖） | `alt="簡短摘要"` + `aria-describedby` 指向完整說明 |

### 5.2 影片與音訊

*   影片必須提供字幕 (Captions)
*   自動播放的影片必須預設靜音，並提供暫停控制
*   不可使用自動播放的音訊

## 6. 表單無障礙 (Form Accessibility)

### 6.1 表單標籤

```tsx
// ✅ 正確 — 明確關聯 label 與 input
<label htmlFor="email">電子信箱</label>
<input id="email" type="email" required />

// ✅ 正確 — 使用 aria-label（無可見 label 時）
<input type="search" aria-label="搜尋商品" placeholder="搜尋..." />

// ❌ 錯誤 — 僅用 placeholder 當標籤
<input type="email" placeholder="電子信箱" />
```

### 6.2 錯誤處理

*   欄位驗證失敗時，錯誤訊息必須以 `aria-describedby` 關聯至對應欄位
*   使用 `aria-invalid="true"` 標記有誤的欄位
*   表單整體驗證失敗時，焦點移至第一個有誤的欄位或錯誤摘要區域
*   錯誤訊息使用 `role="alert"` 或 `aria-live="assertive"` 即時通知

### 6.3 必填欄位

*   使用 `required` 屬性（原生 HTML）
*   同時在視覺上標示必填（如星號 `*`），並在表單頂部說明星號含義
*   星號使用 `aria-hidden="true"` 隱藏，改由 `required` 屬性讓螢幕閱讀器識別

## 7. 動態偏好 (Motion Preferences)

```css
/* 預設提供動畫 */
.animated-element {
  transition: transform 250ms ease-in-out;
}

/* 尊重使用者的減少動態偏好 */
@media (prefers-reduced-motion: reduce) {
  .animated-element {
    transition: none;
  }
  
  /* 或提供更溫和的替代方案 */
  .page-transition {
    animation: none;
    opacity: 1;
  }
}
```

## 8. 測試與驗證 (Testing & Validation)

### 8.1 自動化工具

*   **ESLint：** 安裝 `eslint-plugin-jsx-a11y`，在開發階段即時捕捉無障礙問題
*   **axe-core：** 整合至單元測試（`@axe-core/react` 或 `jest-axe`），在 CI 中自動驗證
*   **Lighthouse：** 在 CI pipeline 中執行 Accessibility audit，分數不得低於 90

### 8.2 手動測試檢核

每次發佈前，至少對關鍵流程執行以下手動測試：

- [ ] 僅用鍵盤完成完整操作流程（不觸碰滑鼠）
- [ ] 使用螢幕閱讀器（NVDA / VoiceOver）走過主要流程
- [ ] 將瀏覽器字型放大至 200%，確認佈局不破裂
- [ ] 使用色彩對比檢查工具（如 Colour Contrast Analyser）驗證所有文字
- [ ] 在 `prefers-reduced-motion: reduce` 下確認無不適動畫
